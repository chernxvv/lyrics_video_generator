# ТЗ для Codex: GUI-приложение для генерации вертикальных lyric-video под трек

## 1. Общая задача

Нужно разработать desktop-приложение с GUI, которое на вход принимает:

- аудиотрек;
- обложку/изображение трека;
- название трека;
- имя исполнителя;
- дату релиза;
- текст трека построчно;
- время начала каждой строки текста в формате `мм:сс`.

На выходе приложение должно генерировать готовый вертикальный видеоролик формата **9:16**, длительность которого **точно равна длительности загруженного трека**.

Приложение должно быть ориентировано на удобную ручную подготовку lyric-video без работы через CLI, JSON, YAML и другие внешние шаблонные файлы.  
**GUI обязателен.**

---

## 2. Цель продукта

Сделать удобный оркестратор/генератор lyric-video, в котором пользователь вручную загружает исходники, задаёт тайминги строк и получает финальный готовый ролик без ручного видеомонтажа.

---

## 3. Основной пользовательский сценарий

1. Пользователь открывает приложение.
2. Загружает аудиофайл трека.
3. Загружает изображение/обложку трека.
4. Вводит:
   - имя исполнителя;
   - название трека;
   - дату релиза.
5. Добавляет текст песни построчно.
6. Для каждой строки указывает **только время начала строки** в формате `мм:сс`.
7. Нажимает кнопку генерации.
8. Получает итоговый видеофайл.

---

## 4. Формат итогового видео

### 4.1. Параметры видео
- Соотношение сторон: **9:16**
- Ориентация: **вертикальная**
- Длительность: **равна длительности аудиотрека**
- Рекомендуемый базовый формат экспорта:
  - контейнер: `MP4`
  - видеокодек: `H.264`
  - аудиокодек: `AAC`
- Рекомендуемое разрешение по умолчанию:
  - `1080x1920`

### 4.2. Компоновка элементов на экране
Элементы должны быть расположены **строго в следующей логике**:

1. **В верхней части экрана**:
   - имя исполнителя;
   - ниже — отдельной строкой символ `—`;
   - ниже — название трека.

2. **Чуть выше центра экрана**:
   - загруженная обложка/картинка трека.

3. **Чуть ниже центра экрана**:
   - область отображения текста песни.

4. **Под текстовым блоком**:
   - дата релиза.

---

## 5. Требования к фону

## 5.1. Общая идея
Фон видео должен быть не статичным, а **живым анимированным мягким градиентом**.

## 5.2. Источник цветов
Цвета фона должны строиться **на основе преобладающих цветов загруженной картинки**.

Нужно:
- проанализировать изображение;
- определить основные цвета;
- учитывать **доминирование цветов по процентному соотношению**;
- использовать именно наиболее выраженные цвета изображения как основу палитры фона.

Пример логики:
- если в изображении больше всего чёрного, синего и белого, то именно эти цвета должны лечь в основу фоновой анимации.

## 5.3. Визуальный стиль фона
Фон должен:
- быть **очень мягким**;
- иметь **плавные переходы**;
- выглядеть как **хаотично переливающиеся цветовые пятна**;
- напоминать **лавовую лампу**, но:
  - без резких границ;
  - без выраженных “капель”;
  - без отвлекающей агрессии;
  - без слишком заметной рваной анимации.

Итог: фон должен быть атмосферным, живым и плавным, но не мешать чтению текста и восприятию обложки.

---

## 6. Требования к отображению текста

## 6.1. Формат входных данных текста
Пользователь вводит текст **построчно**.  
Для каждой строки задаётся **только время начала**.

Пример:

| Время начала | Строка |
|---|---|
| 00:12 | Первая строка |
| 00:18 | Вторая строка |
| 00:24 | Третья строка |

Время окончания строки **не задаётся**.  
Оно определяется автоматически как время начала следующей строки.  
Для последней строки — до конца трека либо до следующей логически допустимой границы.

## 6.2. Логика прокрутки текста
Текст должен отображаться в отдельной **ограниченной области** под обложкой.

Требования:
- область текста фиксированная по размеру;
- текст не должен занимать весь экран;
- прокрутка происходит **построчно**, а не плавным непрерывным бегом;
- смена/сдвиг текста должна происходить **в момент наступления времени начала соответствующей строки**;
- тайминг определяется по тем отметкам `мм:сс`, которые пользователь указал вручную.

Иными словами:
- наступило время строки;
- блок текста смещается так, чтобы актуальная строка стала текущей/центральной/акцентной в зоне просмотра.

## 6.3. Требования к читаемости
Текст должен:
- быть легко читаемым на любом фоне;
- не сливаться с фоном;
- корректно переноситься, если строка длинная;
- не выходить за пределы выделенной текстовой области;
- не перекрывать обложку, заголовок и дату релиза.

---

## 7. Требования к обложке

- Используется изображение, загруженное пользователем.
- Обложка располагается **чуть выше центра экрана**.
- Обложка является одним из центральных визуальных элементов ролика.
- Должна масштабироваться аккуратно, без искажений пропорций.
- Допустим режим вписывания в контейнер с сохранением пропорций.

---

## 8. Требования к метаданным на экране

## 8.1. Верхняя часть
В верхней части экрана должны быть:

1. имя исполнителя;
2. ниже — строка с тире `—`;
3. ниже — название трека.

### Логика:
- имя исполнителя визуально находится выше названия трека;
- название трека находится **над обложкой**;
- все три строки образуют единый верхний информационный блок.

## 8.2. Нижняя часть
Под текстовым блоком должна отображаться:
- дата релиза.

---

## 9. Требования к GUI

## 9.1. Общие требования
Приложение должно быть desktop GUI-приложением.  
Работа только через командную строку не подходит.

Интерфейс должен позволять выполнять весь цикл подготовки ролика без ручного редактирования внешних файлов.

## 9.2. Обязательные элементы GUI

### Блок исходных файлов
- поле/кнопка загрузки аудиофайла;
- поле/кнопка загрузки изображения.

### Блок метаданных
- поле ввода исполнителя;
- поле ввода названия трека;
- поле ввода даты релиза.

### Блок текста и таймингов
Нужна удобная таблица/редактор строк, где для каждой строки есть:
- время начала (`мм:сс`);
- текст строки.

Нужны действия:
- добавить строку;
- удалить строку;
- изменить строку;
- изменить время строки;
- изменить порядок строк при необходимости.

### Блок превью / служебной информации
Желательно предусмотреть:
- отображение длительности загруженного трека;
- мини-превью обложки;
- отображение извлечённой палитры доминирующих цветов;
- базовое визуальное превью композиции кадра.

### Блок генерации
- кнопка запуска генерации;
- выбор пути сохранения;
- индикатор прогресса;
- сообщения об ошибках/валидации.

---

## 10. Валидация входных данных

Приложение должно проверять:

### Аудио
- файл существует;
- формат поддерживается;
- длительность успешно считывается.

### Изображение
- файл существует;
- формат поддерживается;
- изображение успешно открывается и анализируется.

### Тайминги текста
- каждая строка должна иметь время начала;
- формат времени должен быть `мм:сс`;
- время должно быть в пределах длительности трека;
- строки должны быть отсортированы по возрастанию времени;
- не должно быть пустых строк без необходимости.

### Метаданные
- имя исполнителя не пустое;
- название трека не пустое;
- дата релиза не пустая либо имеет допустимый формат.

## 11. Предлагаемый стек технологий

Ниже не просто список, а конкретное назначение каждого слоя.

## 11.1. Язык
**Python**

Почему:
- быстрое прототипирование;
- хорошие библиотеки для GUI, изображений, аудио, видео и рендеринга;
- удобно собрать в desktop-приложение.

## 11.2. GUI
**PySide6** (предпочтительно) или **PyQt6**

Использовать для:
- основного окна приложения;
- форм загрузки файлов;
- таблицы строк и таймингов;
- предпросмотра;
- прогресс-бара;
- управления генерацией.

## 11.3. Работа с изображениями
**Pillow** + при необходимости **NumPy**

Использовать для:
- загрузки изображения;
- ресайза;
- подготовки обложки;
- анализа цветовой палитры;
- извлечения доминирующих цветов.

## 11.4. Извлечение доминирующих цветов
**scikit-learn (KMeans)** или альтернативный аккуратный алгоритм кластеризации

Использовать для:
- поиска основных цветов изображения;
- определения наиболее преобладающих цветов;
- учёта доли каждого цвета в итоговой палитре фона.

## 11.5. Работа с аудио
Минимально:
- **ffmpeg / ffprobe**  
Дополнительно по необходимости:
- `pydub` или `librosa`

Использовать для:
- чтения длительности трека;
- проверки аудиофайла;
- финального muxing видео + аудио.

## 11.6. Генерация видеоряда
Предпочтительно:
- **ffmpeg** как основной движок финального рендера

Допустимо использовать вспомогательно:
- **MoviePy** для прототипа;
- но для стабильного рендера лучше ориентироваться на **ffmpeg + подготовку кадров/слоёв**.

Использовать для:
- сборки итогового видео;
- наложения текста;
- позиционирования элементов;
- анимации;
- финального экспорта.

## 11.7. Отрисовка промежуточных кадров / фоновой анимации
Возможные варианты:
- `numpy + pillow` для генерации кадров фона;
- либо генерация procedural background и последующая передача в ffmpeg.

Цель:
- получить мягкий анимированный “lava-lamp”-подобный фон из доминирующих цветов.

## 12. Предлагаемая модульная архитектура

Нужно реализовать приложение не одной простынёй, а модулями.

### 12.1. `gui/`
Модуль GUI.

Должен отвечать за:
- окно приложения;
- поля ввода;
- таблицу строк;
- кнопки загрузки;
- запуск генерации;
- вывод ошибок и статусов.

### 12.2. `core/audio.py`
Отвечает за:
- чтение аудиофайла;
- получение длительности;
- валидацию формата;
- подготовку информации для финального рендера.

### 12.3. `core/image_analysis.py`
Отвечает за:
- загрузку изображения;
- уменьшение копии для анализа;
- извлечение доминирующих цветов;
- расчёт процентного соотношения цветов.

### 12.4. `core/background.py`
Отвечает за:
- генерацию мягкого анимированного фона;
- использование палитры доминирующих цветов;
- плавные хаотичные переливы;
- экспорт кадров/видеослоя для дальнейшего композитинга.

### 12.5. `core/layout.py`
Отвечает за:
- расчёт позиций всех элементов;
- отступы;
- размеры зон;
- компоновку:
  - артист;
  - тире;
  - название;
  - обложка;
  - текстовый блок;
  - дата релиза.

### 12.6. `core/lyrics.py`
Отвечает за:
- хранение строк текста;
- парсинг времени `мм:сс`;
- сортировку;
- вычисление активной строки по времени;
- логику построчного скролла.

### 12.7. `core/render.py`
Отвечает за:
- сборку всех визуальных слоёв;
- композитинг;
- генерацию финального видеопотока;
- передачу аудио;
- экспорт итогового файла.

### 12.8. `core/validation.py`
Отвечает за:
- проверку входных данных;
- сообщения об ошибках;
- блокировку генерации при невалидных данных.

### 12.9. `models/`
Модели данных.

Например:
- `ProjectData`
- `LyricLine`
- `RenderSettings`
- `PaletteInfo`

## 13. Логика рендера

Ниже логика, которую приложение должно соблюдать.

### 13.1. Подготовка
1. Загрузить аудио.
2. Определить длительность трека.
3. Загрузить обложку.
4. Извлечь доминирующие цвета и их доли.
5. Подготовить список строк текста и таймингов.
6. Проверить валидность всех данных.

### 13.2. Генерация фона
1. На основе доминирующих цветов сформировать палитру.
2. Создать мягкую анимацию цветовых пятен.
3. Сделать переливы плавными и медленными.
4. Избежать резких контрастных скачков.

### 13.3. Сборка композиции
1. Разместить верхний блок:
   - исполнитель;
   - `—`;
   - название трека.
2. Разместить обложку чуть выше центра.
3. Разместить под ней текстовый блок.
4. Разместить под текстовым блоком дату релиза.

### 13.4. Логика текста
1. До наступления времени строки отображается предыдущая актуальная позиция.
2. В момент времени начала новой строки текстовый блок смещается построчно.
3. Переход должен быть визуально аккуратным.
4. Текст не должен перескакивать хаотично.

### 13.5. Экспорт
1. Итоговое видео должно быть длиной ровно как трек.
2. Аудио должно быть синхронно встроено в ролик.
3. На выходе сохраняется финальный MP4.

## 17. Что должно быть на выходе

На выходе должен получаться готовый видеофайл со следующими свойствами:

- вертикальный;
- 9:16;
- длительность = длительности трека;
- в верхней части:
  - исполнитель,
  - тире,
  - название трека;
- чуть выше центра:
  - обложка;
- чуть ниже центра:
  - текст в ограниченной области;
- текст прокручивается **построчно** по заданным временам начала;
- под текстом:
  - дата релиза;
- на фоне:
  - мягкий анимированный градиент;
  - построенный по **преобладающим цветам изображения**;
  - с учётом **процентного доминирования цветов**;
  - визуально похожий на мягкие хаотичные переливы “лавовой лампы”.

## 18. Нефункциональные требования

- Код должен быть структурирован по модулям.
- Код должен быть пригоден для дальнейшего расширения.
- Не делать монолитный скрипт на 1 файл.
- Должна быть явная separation of concerns:
  - GUI отдельно;
  - бизнес-логика отдельно;
  - рендер отдельно;
  - анализ изображения отдельно.
- Все критичные шаги должны логироваться.
- Ошибки не должны падать немой стеной traceback в лицо пользователю.

## 19. Критерии приёмки

Считать задачу выполненной, если:

1. Приложение запускается как GUI.
2. Можно загрузить трек и картинку.
3. Можно ввести исполнителя, название и дату релиза.
4. Можно построчно заполнить текст и тайминги начала.
5. Приложение корректно валидирует данные.
6. Генерируется вертикальный ролик 9:16.
7. Длительность ролика совпадает с длительностью трека.
8. Обложка расположена чуть выше центра.
9. Верхний текстовый блок содержит:
   - исполнителя,
   - тире,
   - название трека.
10. Под обложкой есть ограниченная область текста.
11. Текст двигается построчно по заданным временам начала строк.
12. Под текстом отображается дата релиза.
13. Фон представляет собой мягкий анимированный градиент.
14. Палитра фона берётся из **доминирующих цветов обложки**.
15. При построении палитры учитывается **процентное преобладание цветов**.
16. Итоговый файл экспортируется в видеоформат и воспроизводится без рассинхрона.

## 20. Дополнительные пожелания

Ниже не обязательное, но полезное:

- возможность сохранить проект и открыть его позже;
- быстрый импорт текста сразу списком;
- возможность предпросмотра текущей активной строки;
- настройка шрифтов, размеров, отступов и скорости анимации перехода строк;
- настройка интенсивности/скорости анимации фонового градиента;
- экспорт чернового preview-ролика в пониженном качестве.

## 21. Что важно не забыть при реализации

- Нельзя требовать от пользователя заполнять JSON/YAML руками.
- Нельзя делать интерфейс только через консоль.
- Нельзя игнорировать процентное доминирование цветов картинки при генерации фона.
- Нельзя делать фон резким, рваным или слишком активным.
- Нельзя делать непрерывный бегущий текст вместо построчной синхронизации.
- Нельзя требовать время окончания строки — задаётся только время начала строки.
- Нельзя нарушать заданную компоновку элементов на экране.
